## 3. Behaviour after the SEASON window closed (Step 3)

The window in `release-policy/season-2026-workshop.json` is `2026-08-20T00:00:00Z` to `2026-09-18T23:59:59Z`. Today is 5 October 2026, so the window closed 17 days ago.

### 3.1 What the backend returns after the window

Every match request is rejected before any matching happens.

- `prompt_get` in `django/researchdata/views.py` calls `_parse_match_request`, which calls `validate_request_identity` (`django/researchdata/release_policy.py:113`).
- That function compares the request's `X-ISI-Build-ID` and `X-ISI-Extension-Version` headers with the committed policy, then compares the current time with `active_window`. Outside the window it raises `IdentityError("inactive window")` (line 130).
- `_parse_match_request` turns any `IdentityError` into `MatchContractError(403, 'release_not_allowed')`, and `json_error` returns `{"error": "release_not_allowed"}` with HTTP 403 and `Cache-Control: no-store`. The error text does not say why.
- Identity is checked after the method and content-type checks and the body-size limit, and before the form fields are read. Nothing about the query is looked at, embedded or logged.

I confirmed this on the local SQLite copy with a urlencoded POST carrying the policy's build ID and version, and the query "is keto safe long term":

| `ISI_RELEASE_CLOCK` | Response |
|---|---|
| `2026-09-01T12:00:00+00:00` (inside the window) | 200, `{"prompt": false, "prompts": [], "topics": [], "classifier": "no_match"}` (the local database has no topics, so no match is expected) |
| `2026-10-05T12:00:00+00:00` (after the window) | 403, `{"error": "release_not_allowed"}` |

The clock is the only difference between the two runs. Production never sets `ISI_RELEASE_CLOCK`, so on Render the check uses real UTC time and the window has closed on its own, with no deploy or setting change. Nothing is switched off by hand; the service simply refuses.

Other endpoints are untouched by the window. `_research_writes_blocked` returns true because `RESEARCH_WRITES_ENABLED` defaults to false, so the response and report endpoints, and the third write endpoint that uses the same guard, return 403 `research_writes_disabled` regardless of date.

### 3.2 What a user with the published extension sees

I could not check whether the extension was ever uploaded to the Chrome Web Store (`AGENTS.md` says the store item ID was still pending). The following applies to anyone who has the 0.2.1 build installed, from the store or by loading it unpacked.

- Matching only starts once the user has accepted the in-browser notice (`NOTICE_VERSION` `season-2026-v2`). A user who never accepted sees no request at all.
- After acceptance, `background.js` POSTs to `/data/prompt/get/` with the headers above and gets the 403. `request_lifecycle.js` retries only 502, 503 and 504, so a 403 is not retried.
- `content.js` treats any non-OK response the same way (line 340): it removes any prompt card and mounts the `#isi-badge` signpost in its `error` state. The pill text is "Couldn't reach the server", with a muted dot.
- That wording is misleading for this case. The server is reachable and is deliberately refusing. There is no wording anywhere in the extension that says the workshop has ended, and no code path that distinguishes 403 `release_not_allowed` from a network failure.
- The popup and the consent notice still describe the SEASON 2026 workshop release. I did not test the popup after the window closed.

### 3.3 What the two live endpoints return today

Read-only GETs made on 5 October 2026:

`GET https://investigating-search-interface.onrender.com/healthz` returned HTTP 200:

```json
{"status": "ok"}
```

`GET https://investigating-search-interface.onrender.com/data/release/ready/` returned HTTP 200:

```json
{"ready": true, "failures": [], "policy_sha256": "bd4cc3cee29a5ca464094779a78ef9562719be0f77adc34b96663189a0e8aaa4", "git_commit": "885113b764d4", "build_id": "0.2.1-season-2026-1"}
```

Reading these:

- The live service runs commit 885113b, which is the tip of `main`, so nothing newer is deployed.
- `ready: true` does not mean the service will answer a match request. `evaluate_readiness` in `django/researchdata/release_readiness.py` checks the policy file, threshold, margin, flags, model hashes and topic index. It never compares the clock with `active_window`. Today the endpoint reports ready while every real request gets a 403. `AGENTS.md` already says the endpoint "does not run canaries"; it should also say it does not check the window.
- I did not read `/data/ops/status/` (staff only) and did not send any query to the live service.

I ran the full suite with `ISI_RELEASE_CLOCK=2026-10-05T12:00:00+00:00`, which takes priority over the automatic test freeze. This is the same as removing the freeze, because the real date is now after the window.

Every failure is a test that exercises `/data/prompt/get/` with valid identity headers, or calls `validate_request_identity` directly, and now meets the 403 or the exception. The one policy test that failed directly (`test_valid_workshop_identity_is_accepted`) calls `validate_request_identity` without a `now` argument, so it reads the clock. I did not find a test that checks the window edges with its own `now`, so the window boundary itself appears untested. This confirms the freeze is the only thing keeping the suite green after 18 September. A contributor who runs the suite with `ISI_RELEASE_CLOCK` set to a date after the window, or who sets a dev environment variable by habit, will see 34 failures that are not regressions.

The freeze applies only when `test` is in `sys.argv`. Anyone running the tests through another runner (for example `pytest`) will not get the freeze and will see these 34 failures. The same applies to the local-work recipe in `AGENTS.md`: after 18 September, `ISI_RELEASE_CLOCK` must be set to a date inside the window (the file only says to do this "before 20 Aug").

## 4. Options for the next mode (Step 4)

These are descriptions, not recommendations to implement. All of them would go through a branch and pull request; `main` deploys automatically.

### Option A: stay dormant until a new release

- Code and policy: none. The 403 is the intended behaviour once the window closes.
- Tests: none affected. Keep the frozen test clock.
- Chrome Web Store review: not needed.
- Governance: nothing new. Two small things are worth tidying without changing behaviour: the misleading "Couldn't reach the server" pill (which needs a client change and therefore a new store version, so only worth bundling with a later release) and the `ready: true` on a closed window (server only, a candidate for the next backend change).
- Cost: the Render service is on the Standard plan (`render.yaml`), so it continues to bill while it answers nothing useful. Whether to suspend or downgrade it is Rosie's decision. Suspending it would turn the 403 into a Render error page, and the extension would then show the same "Couldn't reach the server" pill.

### Option B: a private evaluation window for Rosie and invited testers

- Code and policy: new release-policy file or a second window and build ID, so the old workshop build stays closed. The client would need a matching `BUILD_ID` and `EXTENSION_VERSION`, so the extension must be rebuilt. Testers could load it unpacked, which avoids a store review, but unpacked loading is awkward for non-technical testers.
- Tests: `release_policy.py` currently validates `mode == "workshop"` and `capabilities == ["matching"]`, and `workshop_writes_allowed` hard-codes the workshop build. Tests for these, plus the readiness, packaging and client-constant tests, would be touched. The test clock freeze would need a second date.
- Chrome Web Store review: not needed if the build is loaded unpacked. A private or unlisted store listing would need a review.
- Governance: if it stays matching-only with no writes, it is the same data posture as the workshop build, but the privacy notice is titled and scoped to "the SEASON 2026 workshop release" and says other releases have their own notices, so a new notice or a reissue is needed before anyone other than Rosie uses it. Testers' searches are still sent to the server for matching, so the notice must say who they are and what happens to the text.

### Option C: a new public research build

- Code and policy: new policy, new build identity, new notice version, and a new store version. The release freeze constants in `AGENTS.md` (timeouts, host list, selectors) would be reopened.
- Tests: wide. Policy, readiness, packaging, client contract and release-gate tests all assume the single workshop policy.
- Chrome Web Store review: yes, a full review, as for any new version.
- Governance: this depends on what the build does. If it only matches queries and stores nothing, the existing posture could carry over with a new notice. If it stores responses, assigns identifiers or accepts reports, that is a separate, unresolved governance question: `AGENTS.md` records that the ethics application covering `EngagementEvent` and `Response` is not yet submitted. I am flagging this and not proposing an answer. It is Rosie's decision, and it changes the privacy notice, the Limited Use wording and the extension's declared data practices.

### Option D: a no-store, no-window demo mode

- Code and policy: a policy with an open-ended or very long window, matching only, for demos and teaching.
- Tests: the same set as B, plus a test that an open window cannot be combined with writes.
- Chrome Web Store review: same as B or C depending on distribution.
- Governance: an open-ended window removes the natural end date that the workshop notice relies on ("workshop release"). The notice would need to say what the service is, who runs it and how long it will exist. This is the option most likely to be mistaken for an ongoing public service, so the wording matters.
